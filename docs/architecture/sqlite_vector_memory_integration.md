# SQLite/Vector Memory Integration

## Repository Assessment

The repository-level `plugins/memory/` tree contains useful prototypes for
SQLite vector storage, ingestion, entity and fact retrieval, trust scoring,
and governance reports. It is not a production product subsystem as-is:

- it is outside the packaged `project_maya` namespace and is not installed by
  the Project MAYA wheel;
- it contains parallel retrieval APIs and generated bytecode artifacts;
- vector search performs an exact Python scan with no established scale gate;
- parts of the tree contain host-specific paths;
- its `GovernanceValidator` is advisory and does not itself deny access;
- ingestion, storage, and governance errors are suppressed in several paths;
- the legacy test tree requires dependencies absent from the managed runtime.

The useful storage contract has therefore been promoted into the canonical
product package rather than copying the whole prototype tree into the
installer.

## Installed Design

`project_maya.memory.LocalSQLiteVectorRetriever` is the installed local memory
backend. Standard configuration selects `local_vector` with a SQLite registry.
The backend provides:

- customer-controlled SQLite persistence under `MAYA_DATA_DIR`;
- WAL mode, busy timeout, transactional upsert, and deterministic identifiers;
- FTS5 text retrieval and exact cosine-vector retrieval;
- normalized trust and provenance fields;
- a single persisted and validated embedding dimension;
- redacted statistics and SQLite integrity health checks;
- transaction-consistent backup through SQLite's backup API, excluding WAL and
  shared-memory sidecars from archives.

Every product-facing remember, recall, and search operation passes through
`GovernedMemoryRetriever`. The authorization result is written to Maya's local
JSONL audit sink without record bodies or secrets.

## Hermes Integration

Standard first-run setup creates a Maya-owned Hermes provider shim under:

```text
<MAYA_DATA_DIR>/hermes/plugins/maya/__init__.py
```

It updates the customer-local Hermes configuration to select external provider
`maya` while preserving or initializing Hermes' normal `memory_enabled` and
`user_profile_enabled` settings. The shim loads
`MayaHermesMemoryPlugin` from the installed Project MAYA package. Hermes
continues to store sessions, `MEMORY.md`, and `USER.md` through its built-in
memory. Maya provider turn synchronization is a no-op. Only explicit governed
Information Manager ingestion and search operate on the SMB SQLite store.

This uses Hermes' public memory-plugin discovery contract. The existing
`HermesMemoryProviderBridge` was not modified. Installed qualification checks
that the `maya` provider is discoverable and available, and separately proves
that governed writes and reads reach a healthy SQLite database.

## Governance Status

Governance is integrated, not merely source-controlled:

- runtime execution passes through `GovernedAgentRuntime`;
- external model inference requires a separate `model.egress` decision;
- memory reads and writes pass through `GovernedMemoryRetriever`;
- decisions are recorded in the local audit sink;
- the Standard starter policy is deny-by-default and grants only the core
  local runtime, configured model inference, and governed memory operations;
- connector and other external mutations remain denied until explicit setup
  adds the relevant policy and authorization.

## Remaining Qualification Work

The backend performs local embedding generation and hybrid FTS/vector ranking
when a pinned, hashed ONNX model, tokenizer, NumPy, ONNX Runtime, and tokenizers
wheel are present. Setup leaves lexical retrieval available and reports
semantic readiness blocked when they are absent. Retention enforcement,
contradiction resolution, and a benchmarked large-collection vector index
remain readiness items. A production Windows support claim still requires rebuilding the
installer and passing clean-install Hermes lifecycle, setup, health, backup,
restore, update, rollback, and secret-safety qualification.

The prepared `embedding_model` dependency archive must contain these files at
its root:

```text
embedding-model-manifest.json
model.onnx
tokenizer.json
```

The manifest records `model_id`, immutable `revision`, `license`, HTTPS
`source`, `dimension`, `max_length`, and SHA256 values for `model.onnx` and
`tokenizer.json`. The release builder validates this metadata and does not
download a model during installation. Embedding rebuild computes all vectors
first, authorizes every persistent-memory update, then replaces the derived
vectors in one SQLite transaction.
