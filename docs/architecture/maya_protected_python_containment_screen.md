## Evidence Rules

`ContainmentEvidence.cs` is a pure decision helper, now wired by the setup host. Its inert
fixture executable calls no Windows security, network, token or product startup
API. It distinguishes allowed controls from denied operations and rejects missing,
unknown, incomplete, unsupported and timed-out observations as successful proof.
A witnessed unauthorized effect wins over incomplete capture and fails the probe.

The caller, not a child-supplied report, must supply the frozen requirements and
admitted native-error sets. The helper does not parse/admit report bytes, bind
target identity, verify controls, authenticate claims or enforce the size caps.
`ContainmentScreen.cs` supplies host-frozen requirements, byte limits, strict
duplicate-rejecting ASCII JSON admission, attempt identity, fixture controls and
postconditions. The fixed child report remains untrusted. No result from this
parser can replace native effect evidence or independently qualify containment.

A successful bind is not automatically an escape: it may precede blocked traffic.
A UDP timeout or silent drop is not an explicit native denial. A host endpoint's
positive control establishes reachability from the host, not from AppContainer.
Zero packets without a verified attempted operation cannot establish containment.
Do not attribute an observed denial specifically to WFP rather than zero-capability
AppContainer policy without evidence distinguishing the mechanisms.

Any unauthorized effect stops remaining probes. Missing prerequisites, unavailable
aliases, capture loss or exhausted deadline produce blocked/inconclusive evidence,
never a pass. Even complete expected observations produce only
`screen_completed_not_containment_qualified`. Production and containment remain
false; Hermes, Gate A, connectors, gateway and Metabase remain unqualified.

## Screen 9 Correction Scope

Version becomes 0.1.0-screen.9 / assembly file version 0.1.0.9; scope remains
synthetic-containment-screen-v1. Only these product changes are included:

1. A fixed request builds the attempt's existing protected document base path
   and appends the literal `:maya-screen`. Check the ordinary base path for links;
   do not submit the ADS pathname to Framework file-path validation.
2. CreateFileW uses GENERIC_WRITE / CREATE_NEW for creation and GENERIC_READ /
   OPEN_EXISTING for readback, FILE_SHARE_READ and FILE_ATTRIBUTE_NORMAL. No
   alternate target, stream name, overwrite attempt or fallback is accepted.
3. Transfer the returned non-inheritable handle into an owning SafeFileHandle
   and the handle-based FileStream constructor. Constructor failure disposes the
   owned handle; normal stream disposal closes it. These handles exist before
   child launch or after confirmed stop, not in its inheritance list.
4. Write the exact 32-byte ASCII attempt nonce and flush it durably. Readback is
   byte-exact and bounded to 33 bytes: short, different and oversized contents
   fail. Read/open failures preserve the failed host postcondition and safe native
   reason code. No global path-handling switch or extended-path fallback is added.
5. Record fixed setup/evidence/cleanup stage names and numeric exception HRESULTs
   separately. Original failure stage survives later cleanup. Do not log raw
   exception messages, stacks, private contents or arbitrary filenames.

Native lifecycle correctness is not established by compilation or memory-stream
tests. This preparation does not change payload bytes, notices, 48 cases, native
admitted-error sets, ACL/label policy, capabilities, token checks, WFP rules,
endpoints/IPC, job/child policy, 22/30-second budgets, output limits, evidence
predicates or cleanup policy. No unrelated defect, journal-gap fix, new runtime,
supervisor, debugger, security grant or automatic retry is included. Separate
artifact/impact review, run approval and fresh product consent remain required.
